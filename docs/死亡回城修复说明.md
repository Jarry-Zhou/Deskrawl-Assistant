# 1.2.8 死亡回城修复说明

基于 v1.2.8 修复死亡后的托管返回流程。本文区分源码、离线回归和只读实机检查，不将结构检查当作实机动作验收。

## 问题与原因

实机日志显示：死亡后调用普通 TownPortalSystem 返回入口，助手认为已请求回城；角色之后仍在原关卡，等待 45 秒或扩展到 120 秒后停止托管。该入口没有经过 DeathUI 的 BackToTownButton 处理，未取消自动复活计时，也没有进入死亡结算的返回流程。

只读分析 Deskrawl 1.0.2b 的方法和按钮绑定确认：DeathUI.gbi 为返回主城处理，清除自动复活计时并设置请求标记，调用 GameManager.dnw；ReviveButton 对应另一入口。新增方法、类型字段、TypeInfo 地址和冷启动编码均绑定现有严格构建哈希，不放宽版本校验。

## 修复行为

- 死亡时使用游戏死亡界面的返回主城处理；存活和通关保持原有返回流程。
- 死亡界面尚未加载或已有复活／回城请求时等待，不重复提交。
- 死亡优先于商人及成长读取；没有波次计划也能请求回城。
- 读取死亡标记时，将仍显示运行／完成的旧关卡计划标记为失败，防止误算成功。
- 只有确实进入主城才整理奖励和继续刷关，不把原地复活当成回城。

## 验证边界

961 项 Python 测试和 77 项前端逻辑测试通过；离线回归涵盖新入口、冷类型及空实例、自动复活竞争、旧计划死亡标记以及回城后再次入图。打包版在隔离数据目录完成独立窗口及接口启动检查。实际游戏仅只读核验类型字段和版本兼容，没有执行死亡回城、购买、出售或刷图；死亡动作及回城后续刷仍需实机确认。

新 exe 需要退出旧助手后使用；保留原有 runtime-paths.json 的数据与缓存目录。若游戏已因旧请求卡在场景切换中，应先用游戏自身操作恢复至主城或重新进入角色，再验证下一次死亡后的自动回城与续刷。最终实机结果由用户确认。
